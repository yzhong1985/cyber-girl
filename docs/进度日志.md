### 一、铺垫语("让我想想哈")+ 并行执行

- 目标：说完话到真正回复中间那~14s空白是当前体验最大的痛点。做法：VAD一检测到用户说完话，立刻从预生成好的过渡语视频池里随机挑一段推给播放页占位，真正的STT→LLM→TTS→Ditto在其它线程里正常并行跑(管线本来就是VAD/STT/LLM/LMProcessor/TTS各一个线程+队列串联，"并行"是现成的，不用额外写并发代码)，跑完了正式回复自然排在过渡语后面播(复用现成的SSE播放队列，`player.html`完全没改)。
- **角色配置**：`characters.json` 每个角色加 `fillers` 数组(贴合语气，比如小满"让我想想哈"，凛"嗯…")，`voice_registry.py` 加 `current_fillers()`，没配就有兜底默认值。
- **Ditto 侧**(`avatar_service.py`)：新增 `POST /reset_fillers`(清空池子)、`POST /generate_filler?index=N`(生成一段过渡语视频，固定文件名 `filler_N.mp4`，不进 `seg_*` 清理、也不直接推播放，只存进池子)、`GET /play_filler`(随机挑一个已生成好的推给播放页，几乎零延迟，不用 `_gen_lock`)。把原来 `_generate()` 里的核心渲染逻辑拆成 `_render()` 共用。
- **TTS 侧**(`qwen3_tts_handler.py`)：`warmup()` 之后，avatar 模式下用当前角色音色合成 fillers 列表逐个 POST 给 `/generate_filler` 预生成缓存；注册了 `registry` 切角色回调，换角色(=换音色)时后台线程重新生成一遍，不阻塞切换面板的请求。
- **VAD 侧**(`vad_handler.py`)：`speech_stopped` 那一刻，fire-and-forget 开个子线程 `GET /play_filler`，绝不阻塞 VAD 自己的处理循环；不影响非 avatar 模式(没设 `DITTO_AVATAR_URL` 就是空操作)。
- 新增开关 `AVATAR_FILLER`(默认1，`config.env`/`start_avatar.sh` 导出到管线进程的环境变量，`--web`和本机模式通用)。
- **实测**(模拟真实语音输入，`wss://127.0.0.1:8765`)：`speech_stopped` 到过渡语视频出现在 SSE 队列里 **延迟基本为0**(同一秒内)，正式回复照常在 10~14s 后跟上；两次不同请求分别随机挑到了 `filler_3`/`filler_4`，随机选择生效。

### 二、顺带挖到一个更严重的坑：网页版断线一次就永久卡死整条管线

- 起因：验证铺垫语要连续测好几轮对话，第二轮开始VAD突然完全没反应——一查发现不是铺垫语的问题。
- 根因：`connections/websocket_streamer.py` 里，最后一个 WS 客户端断开时会往 `input_queue` 塞一个 `b"END"`。`baseHandler.py`(所有 handler 共用的基类) 收到 `b"END"` 会直接 `break` 退出线程，并且把 `b"END"` 接力放进自己的 `queue_out`——也就是**这一个哨兵值会顺着 VAD→STT→LLM→LMProcessor→TTS 一路传下去，把全部5个 handler 线程依次杀死**，只有重启整个管线进程才能恢复。这套机制显然是给"一个客户端从连接到断开对应一次进程生命周期"的批处理场景设计的(比如原版 `socket` 模式)，不适合网页版这种要长期挂着服务、客户端会反复连接断开(刷新页面/切后台/wifi抖动都算)的持久服务场景。
- 之前几轮真机测试之所以没暴露这个问题，是因为每次我都重启了管线进程去开 debug 日志排障，凑巧每次用户测试前都是"全新进程的第一个连接"，从没真正测过"断开重连"这条路径。
- **修复**：`websocket_streamer.py` 里去掉了这段"最后一个客户端断开就塞 b"END""的逻辑，直接删掉。管线现在断线后就是单纯地空闲等待(should_listen保持原状，不影响)，下一个客户端连上时(`_handle_client`前面已有的逻辑)会重新 `should_listen.set()`，自然衔接上，不需要重启任何东西。
- **实测**：同一个管线进程里连续两轮"连接→说话→收到回复→断开"，第二轮 VAD/STT/LLM 全部正常工作，过渡语/正式回复都正常触发——此前这个场景是完全失效的。

### 一、lmdm 接上 torch.compile，fps 从 19.8 跳到 31.9(本日主线)

- 起因：`scripts/build_onnx_hybrid_cfg.py` 顶部注释写着"lmdm 已用 torch.compile，当前部署"，但翻 `avatar_service.py` 发现只有 `warp_network` 真正接了(158~160行)，lmdm 那部分代码里根本没有——**文档写了，代码没做**，是上次会话留下的半截活。
- 补上：`avatar_service.py` 里给 `_sdk.audio2motion.lmdm.model.model.forward`(即 `MotionDecoder.forward`，`guided_forward` 内部会调它两次做 CFG)套 `torch.compile(mode="default")`，加了独立开关 `_compile_lmdm` / `--no-compile-lmdm` / `AVATAR_COMPILE_LMDM=0`，跟 `_compile_warp` 同一套写法。default 模式(不开 CUDA Graph)是必须的：试过 `reduce-overhead` 会跟内部 rotary embedding 的张量缓存冲突崩溃(`CUDAGraphs 输出被后续运行覆写`)。
- 用 `_fps_test_trtwarp.py`(仿照已有的 `_fps_test.py`，跑2轮吸收编译预热取稳态)实测：**19.8fps(仅warp编译) → 31.9fps(warp+lmdm都编译)**，+61%；相对最早纯PyTorch基线(12.5fps) **+155%**。比之前文档里猜测的"21~22fps"高出不少，实测数字已写回 `avatar_service.py` 和 `build_onnx_hybrid_cfg.py` 的注释里。
- 待办里"上实时后端"这条已经标完成——目标 30~40fps 靠 torch.compile 就摸到了下限，没有再上完整 TRT 图优化的必要了(见下一节)。

### 二、TensorRT warp_network 路线：验证过、没有采用

- 本机(RTX5090/Blackwell + TensorRT 10.14)重新编译了 `GridSample3D` 自定义算子的 TensorRT 插件(`third_party/grid-sample3d-trt-plugin`，Ditto 仓库自带的预编译版是老架构/老TRT版本，本机跑不了)。插件自带的正确性测试脚本有个小 bug(TRT10 输出张量 key 名跟脚本硬编码的不一致)，改成取 `output.values()` 后跑通：跟 `F.grid_sample` 的差异在 FP16 精度噪声范围内，插件本身没问题。
- 发现 `core/models/warp_network.py` 走 `.engine` 路径时用的 `load_model()→TRTWrapper(model_path)` 根本没传 `plugin_file_list`，自定义插件不会被加载——这是 Ditto 上游代码里 TRT-warp 分支本来就没打通的一处坑。补丁：`WarpNetwork.__init__` 遇到 `.engine`/`.trt` 后缀时直接构造 `TRTWrapper(model_path, plugin_file_list=[...])`，指向本机编译的插件 `.so`。
- 用 `scripts/cvt_onnx_to_trt.py` 里现成的 `onnx_to_trt_for_gridsample()` 把 `warp_network.onnx` 转成本机可用引擎(`checkpoints/ditto_trt_custom/warp_network_fp16_local.engine`，~48s 编译)，配了一份对应 cfg(`v0.4_hubert_cfg_onnx_trtwarp_local.pkl`)。
- **结果：fps 跟 torch.compile 版打平(~19.6~20.3 vs 19.8)，没有额外收益**。TRT 版省了 torch.compile ~70s 的首次编译预热，但这个预热本来就被启动时的待命循环吸收了，用户侧感知不到差别。多引入一个第三方插件编译依赖换不来实质提速，**结论：不采用，保留验证过程记录，以后不用再走一遍这条路**。

### 四、端到端链路延迟实测：LLM 几乎免费，Ditto+TTS 才是大头

- 起因：Ditto 提速到 31.9fps 后，想知道现在瓶颈到底在哪，别在已经不是瓶颈的地方继续使劲。用真实的角色 system_prompt(`characters.json` 里小满，204字) + `openai` 库直连本机 `llama-server` 分别测了 LLM / TTS(`faster_qwen3_tts`) / Ditto(`avatar_service.py`)三段。
- **LLM 几乎不是瓶颈**：`llama-server` 有 prompt 前缀缓存，同一个 system_prompt 第二次起的请求 TTFT 从冷启动的 ~4~8s 直接掉到 **~0.1~0.3s**(生成~50字本身只要0.3s)。真实对话里 system_prompt 从第一轮起就固定不变，所以**稳态每轮 LLM 只要约0.2~0.3s**。
- 顺手验证了一个"流式输出没意义"的判断：`LLM/openai_api_language_model.py` 里流式分句用的是 `nltk.sent_tokenize`(英文分词器)，识别不了中文的"。！？"，就算开 `--open_api_stream` 也基本等于没分句——但反正 LLM 已经够快，不值得为这个去修。
- **发现并修了一个真 bug**：`OpenApiModelHandler.warmup()`(`LLM/openai_api_language_model.py:83-96`)预热用的是硬编码的"You are a helpful assistant"+"Hello"，跟真实角色的 system_prompt 对不上前缀，等于没预热到点子上——每次重启服务后**第一轮真实对话**都要重新扛一次 ~4~8s 的冷启动。改成用 `self.chat.to_list()`(已含真实 system_prompt) + 占位user消息去预热，不写回 `self.chat`(不污染正式对话历史)。验证：`setup()`阶段吸收 5.17s 预热成本，紧接着第一轮真实对话只要 **0.24s**(改前会是~4~8s)。
- **TTS 合成**(`faster_qwen3_tts`，CUDA Graph 版)：典型50字回复(合成出8.7s音频)耗时 **~4.5s**(首块0.25s)，实时倍率约0.5(比播放快一倍)。
- **Ditto 生成**：同一段8.7s音频经 `avatar_service.py` 完整HTTP流程(含RVM抠图关闭)耗时 **~9.5s**，实时倍率约1.1(和播放时长基本打平)。
- **端到端(稳态对话，用户说完到视频开始播)：LLM 0.2s(2%) + TTS 4.5s(31%) + Ditto 9.5s(66%) ≈ 14s**。Ditto仍是大头，其次TTS，LLM可以忽略；三者(TTS/Ditto)都跟回复音频时长基本线性，除了回复长度这个已有的调节杆，目前架构下没有更容易拿的延迟收益了——再往下降得是真正的流式架构(TTS边合成边喂给Ditto、Ditto边生成边推流)，工作量接近重新设计，暂不做。

### 七、真机测试(局域网手机浏览器)踩出的两个真 bug

用户拿手机在局域网实测，一开始"看到人、麦克风也授权了，但说话没反应"，排查出两处问题，都已修复并让用户在真机上确认过多轮对话稳定：

- **bug1（player.html）**：`AudioWorkletNode` 只 `src.connect(node)`，没再连到 `audioCtx.destination`——很多浏览器实现里，音频图只有能连到输出的那部分才会被真正拉动处理，悬空节点的 `process()` 回调根本不会被调用，麦克风数据从没进过 worklet。修复：`node` 经一个增益为0的 `GainNode` 接到 `destination`，既能让 worklet 持续跑，又不会把麦克风声音回放出来(避免回声/啸叫)。
- **bug2（`STT/whisper_stt_handler.py:125`，跟网页版无关，本机模式一样会中）**：无条件读 `pred_ids[0, 1]` 当语言token，但极短/近静音的输入(VAD判定为"说话"但内容太少，真实麦克风比本机测试更容易碰到)有时 Whisper 只生成1个token，索引越界直接把整个 handler 崩掉。**更要命的是**：崩溃后这句话没有产出，流程卡在 STT 这一步，下游 TTS 那句"生成完把 `should_listen` 重新置位"永远不会执行——**麦克风从此永久卡死，直到有新客户端连接重置**，现象上跟"完全没反应"一模一样，且没有任何用户可见的报错。修复：`pred_ids.shape[1] <= 1` 时直接退回上一次识别到的语言，不再取那个不存在的token。
- 排障过程：用 `--log_level debug` 重跑管线（`baseHandler.py` 里每个 handler 的 `logger.debug` 计时/内容默认不输出，调试必须显式开），配合 `speech_started`/`speech_stopped`/`assistant_text` 这几个已有的 WS 消息，才在日志里对上号——纯靠前端现象("没反应")完全定位不到是 STT 崩了。
- **遗留的系统性风险(本次未处理)**：`BaseHandler.run()` 对 `process()` 的异常处理只是 `logger.error` 记一下，不会做任何恢复；只要 VAD→STT→LLM→LMProcessor→TTS 链路中任意一环再抛别的异常，还是会复现"卡死到下一次重连"这个模式，只是这次的具体诱因(短音频)已经堵上。如果以后再遇到"看着连上了但没反应"，先怀疑这条链路上有没有新的未捕获异常。
